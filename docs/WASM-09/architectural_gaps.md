# Критический анализ архитектурных рисков и ограничений (Architectural Gaps & Risks)

В данном документе анализируются потенциальные уязвимости, проблемы масштабирования и "узкие места" спроектированной архитектуры Durable WASM на базе PostgreSQL и Sequin, а также предлагаются технические решения для их устранения при переходе в промышленную эксплуатацию (Production-ready).

---

## 1. Риск Split-Brain и гонки записей (Concurrent Execution & Fencing)

### Проблема:
В распределенной системе хост-ноды вычислений могут испытывать задержки (проблемы с GC в Go, сетевые сплиты, высокая утилизация CPU).
* **Сценарий**: 
  1. Хост А берет задачу `Instance-1` и начинает выполнение.
  2. Сеть между Хостом А и PostgreSQL временно деградирует. Хост А не успевает отправить Heartbeat в течение таймаута видимости (Visibility Timeout) в Sequin.
  3. Sequin считает Хост А упавшим и возвращает задачу в очередь.
  4. Хост Б забирает задачу `Instance-1`, считывает состояние и запускает воркер параллельно.
  5. Хост А «отвисает» и пытается записать результаты своего шага.
* **Результат**: Данные будут повреждены, возникнет состояние гонки на запись дельт памяти и Oplog.

### Решение (Optimistic Concurrency Control / OCC):
Ввести понятие **версии эпохи (Epoch / Sequence Number)**:
1. В таблицу `instances` добавляется колонка `version INT DEFAULT 0`.
2. При взятии задачи хост считывает текущую версию.
3. При записи чекпоинта хост выполняет запись только при условии совпадения версии, атомарно инкрементируя её:
   ```sql
   UPDATE instances 
   SET version = version + 1, updated_at = NOW() 
   WHERE id = :instance_id AND version = :expected_version;
   ```
4. Если запрос обновил 0 строк, хост понимает, что его блокировка устарела и выполнение перехвачено. Хост немедленно прерывает выполнение (abort) текущего WASM-инстанса.

## 2. Бесконечный рост Oplog (Oplog Growth & Truncation)

### Проблема:
Воркер может жить днями и совершать тысячи внешних вызовов.
* Таблица `oplog` для одного инстанса будет раздуваться до миллионов строк.
* При перезапуске (Recovery) фаза Replay (проигрывание всех вызовов с шага 1) будет занимать минуты, что делает систему неэффективной.

### Решение (Oplog Truncation):
Связывать Oplog с точками полных снапшотов памяти (Full Snapshots):
1. Периодически (например, раз в 100 шагов Oplog или при достижении критического размера лога) хост принудительно делает **полный снапшот памяти** (вместо инкрементального) и сохраняет его в таблицу `snapshots`.
2. После успешной записи полного снапшота все старые записи Oplog (с индексами меньше текущего `call_index`) становятся не нужны для восстановления, так как состояние памяти уже зафиксировано на этой точке.
3. Хост выполняет очистку:
   ```sql
   DELETE FROM oplog WHERE instance_id = :instance_id AND call_index < :current_call_index;
   DELETE FROM memory_deltas WHERE instance_id = :instance_id;
   ```
   *Это гарантирует, что размер Oplog и количество дельт для восстановления всегда ограничены константным числом.*

## 3. Недетерминизм WebAssembly (Float Operations & NaN)

### Проблема:
Durable Execution фундаментально опирается на детерминизм. Однако в стандарте WebAssembly есть темные углы недетерминизма:
* **Операции с плавающей точкой (Floating Point)**: Спецификация WASM разрешает рантаймам возвращать разные битовые представления для значений `NaN` (Not-a-Number). Если хост-ноды вычислений работают на разных процессорах (например, часть на Intel/AMD x86, часть на Apple Silicon/Graviton ARM), результаты вычислений float-переменных в памяти могут побайтово разойтись. Это нарушит поблочную валидацию хэшей Dirty-Pages.
* **Системные импорты времени**: Использование встроенных функций получения времени (WASI `clock_time_get`) без явного логирования в Oplog приведет к разным путям выполнения кода при Replay.

### Решение:
1. **Канонизация NaN (NaN Canonicalization)**: Включить в конфигурации `wasmtime.Config` принудительную канонизацию float-операций:
   ```go
   config := wasmtime.NewConfig()
   config.SetWasmRelaxedSimd(false) // Отключить расслабленный SIMD
   // Использовать компиляцию с строгим детерминизмом float, если поддерживается
   ```
2. **Строгая изоляция времени**: Запретить WASM-модулям вызывать системные часы напрямую. Все замеры времени должны идти только через хост-функцию (например, `host_get_time`), возвращающую результат, логируемый в Oplog.

## 4. Сборка мусора завершенных воркеров (Garbage Collection of States)

### Проблема:
При завершении процесса (статус `completed` или `failed`) данные из `memory_deltas` и `oplog` должны быть удалены. В случае аварийного завершения или ручной отмены процесса в БД могут остаться «сиротские» строки (orphaned rows), которые со временем переполнят хранилище.

### Решение:
Внедрить каскадное удаление (Foreign Key Cascade) и фоновый процесс очистки:
1. Все таблицы (`memory_deltas`, `oplog`, `tasks`) ссылаются на `instances(id)` с помощью `ON DELETE CASCADE`.
2. При завершении процесса хост выполняет один запрос `DELETE FROM instances WHERE id = :instance_id`, и все связанные данные удаляются автоматически.
3. Реализовать фоновый Worker в Go, который раз в сутки очищает старые зависшие инстансы:
   ```sql
   DELETE FROM instances WHERE status = 'failed' AND updated_at < NOW() - INTERVAL '30 days';
   ```
