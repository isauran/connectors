# Архитектурное предложение (Architecture Proposal): Распределенный Durable WASM движок

Цель данного предложения — спроектировать целевую архитектуру для движка `durable-wasm`, которая гарантирует горизонтальное масштабирование (Scale-Out) по вычислениям и хранению, высокую доступность (High Availability, HA) и надежность выполнения бизнес-процессов (Exactly-Once Semantics).

---

## 1. Обзор целевой архитектуры

Целевая архитектура разделяет **вычисления (Compute)** и **состояние (Storage)**. Это классический подход для облачных систем (Cloud-Native), позволяющий масштабировать их независимо друг от друга.

```
                      +-------------------+
                      |   API Gateway /   |
                      |   Orchestrator    |
                      +---------+---------+
                                |
                                v
                      +-------------------+
                      | Task Queue / Locks| (etcd / Redis / PG Queue)
                      +---------+---------+
                                |
        +-----------------------+-----------------------+
        |                                               |
        v                                               v
+-------+---------------+                       +-------+---------------+
| Stateless Compute Node|                       | Stateless Compute Node|
|  (Go + Wasmtime)      |                       |  (Go + Wasmtime)      |
+-------+---------------+                       +-------+---------------+
        |                                               |
        +-----------------------+-----------------------+
                                |
                                v
                      +-------------------+
                      | Distributed DB    | (CockroachDB / PostgreSQL Cluster)
                      +-------------------+
```

### Основные компоненты системы:
1. **Stateless Compute Nodes (Узел вычислений)**:
   * Хост-приложения на Go, которые не хранят локального состояния воркеров на диске. Они содержат только кэш скомпилированных WASM-файлов.
   * Принимают задачи из очереди, загружают состояние воркера из распределенной БД, выполняют код в `Wasmtime` и записывают изменения обратно.
   * При падении ноды выполнение воркера перехватывается другой нодой.

2. **Distributed Storage Engine (Распределенная СУБД)**:
   * Единый источник правды для хранения журнала операций (Oplog), метаданных воркеров и снимков памяти.
   * Для масштабирования записи и транзакционной целостности используются распределенные реляционные БД (например, **CockroachDB**, **YugabyteDB** или кластер **PostgreSQL**).

3. **Distributed Lock & Queue Manager (Координатор задач)**:
   * Отвечает за распределение воркеров между нодами вычислений.
   * Гарантирует **Single-Active-Instance**: в один момент времени один инстанс воркера выполняется строго на одной ноде вычисления. Это предотвращает состояние гонки (Race Conditions) и дублирование выполнения.
   * Инструменты: **etcd** (или Consul) для распределенных блокировок (Leases) либо распределенная очередь задач на базе **Redis** (с Redlock) или **PostgreSQL** (`SELECT FOR UPDATE SKIP LOCKED`).

## 2. Жизненный цикл выполнения и отказоустойчивость

Для обеспечения надежности и семантики Exactly-Once при крахе любых компонентов системы, жизненный цикл выполнения воркера строится следующим образом:

### А. Запуск и получение задачи
1. Хост-нода берет свободную задачу (инстанс воркера) из очереди задач и накладывает распределенную блокировку (Lock) на этот `instance_id` с таймаутом (например, 10 секунд).
2. Нода считывает из распределенной БД текущий статус воркера:
   * Если это новый воркер — инициализирует чистую память WASM.
   * Если воркер восстанавливается после сбоя — считывает последний снимок памяти (Snapshot) и журнал операций (Oplog).

### Б. Выполнение шагов и перехват сайд-эффектов (Oplog Replay)
1. Нода запускает выполнение кода внутри Wasmtime.
2. При вызове воркером внешней функции (например, отправка HTTP-запроса через импорт WASI):
   * Хост проверяет Oplog по порядковому номеру шага `call_index`.
   * **Replay**: Если запись в Oplog уже существует (это повторный запуск после сбоя), хост не делает реальный запрос, а возвращает сохраненный ответ из БД.
   * **Execution**: Если записи нет (это новое выполнение), хост выполняет реальный сетевой запрос, получает ответ и записывает его в Oplog в БД.
3. Раз в N шагов или при завершении транзакции хост делает чекпоинт: обновляет блокировку (Heartbeat) воркера в координаторе задач, сбрасывает накопившийся Oplog и дельты памяти в распределенную БД.

### В. Обработка аварий (Failover)
* Если хост-нода внезапно падает (Hardware Failure, Out of Memory, сетевой сплит):
  1. Через некоторое время истекает время распределенной блокировки (Lease) для данного `instance_id` в Координаторе.
  2. Другая свободная хост-нода видит зависшую задачу в очереди, забирает ее и накладывает блокировку на себя.
  3. Новая нода восстанавливает состояние воркера из распределенной БД по последнему снапшоту памяти + доигрывает Oplog.
  4. Выполнение воркера продолжается с точки последнего успешного чекпоинта. Для внешнего мира процесс выглядит непрерывным, а побочные эффекты не дублируются.

## 3. Решение проблемы I/O и масштабирования хранилища

Чтобы база данных не испытывала перегрузок при записи тяжелых снапшотов памяти, архитектура применяет двухэтапное сжатие состояния:

### 1. Первичный источник — Oplog (Append-Only)
Большую часть времени воркер совершает небольшие шаги (вызовы API, ветвление логики). Вместо записи всей памяти (мегабайты), хост пишет в БД только строчки Oplog (килобиты). Запись в режиме Append-Only (добавление строк) является самой быстрой операцией для распределенных БД и легко масштабируется горизонтально.

### 2. Инкрементальные снимки (Delta Snapshots)
Раз в несколько десятков шагов или при достижении лимита лога хост делает снимок памяти воркера:
* С помощью флагов страниц Wasmtime хост считывает только список модифицированных страниц (Dirty Pages) размером 4 KB.
* В базу данных записываются только дельты.
* Это снижает объем операций записи на **95-99%** по сравнению с полным копированием памяти.

## 4. Рекомендуемый технологический стек

Для обеспечения надежности корпоративного уровня предлагается следующий проверенный стек технологий:

| Компонент | Выбор технологии | Почему именно это? |
| :--- | :--- | :--- |
| **Вычисления** | Go + Wasmtime SDK | Wasmtime — самый быстрый и безопасный рантайм WASM промышленного уровня (написан на Rust, поддерживается Bytecode Alliance). Go обеспечивает простую интеграцию с облачной инфраструктурой и отличный параллелизм через горутины. |
| **База данных** | CockroachDB (или PostgreSQL в кластере) | CockroachDB — это распределенная SQL СУБД с транзакционной консистентностью (ACID) уровня Serializable. Она масштабируется горизонтально простой добавкой нод, поддерживает автоматическое секционирование (sharding) и устойчива к выходу из строя целых дата-центров. |
| **Координация / Очереди** | Redis (с Redlock) или etcd | `etcd` обеспечивает сильную согласованность (CP в CAP-теореме) и идеально подходит для управления блокировками воркеров (leases). Redis обеспечивает сверхнизкие задержки при распределении задач через очереди. |
| **Репликация и бэкап** | Облачное S3-хранилище | Архивация журнала Oplog и снапшотов в холодное хранилище (AWS S3, GCP Cloud Storage) для долгосрочного аудита и восстановления после глобальных катастроф. |

## 5. Выводы и преимущества целевой архитектуры

* **Бесконечное масштабирование по вычислениям**: Любое количество нод вычислений (Go-сервисов) можно запускать в Kubernetes. При росте нагрузки Kubernetes автоматически масштабирует поды.
* **Линейное масштабирование по данным**: Добавление новых нод в кластер CockroachDB пропорционально увеличивает лимиты по IOPS записи и объему хранения.
* **Надежность 99.999%**: Выход из строя любой хост-ноды или ноды базы данных не приводит к прерыванию бизнес-процессов.
* **Exactly-Once**: Перехват вызовов WASI гарантирует отсутствие повторных сайд-эффектов при сбоях, что критично для финансовых и enterprise-интеграций.
