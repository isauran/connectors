# Архитектурное предложение (Architecture Proposal): Распределенный Durable WASM на базе PostgreSQL и Sequin

Цель данного предложения — спроектировать надежную и масштабируемую архитектуру для движка `durable-wasm`, используя классическую СУБД **PostgreSQL** в качестве основного хранилища и open-source CDC-движок **Sequin** для построения реактивной очереди задач. Это позволяет полностью убрать паразитный поллинг базы данных, повысить пропускную способность системы и сохранить простоту инфраструктуры без внедрения сложных брокеров вроде Kafka или RabbitMQ.

---

## 1. Обзор целевой архитектуры

Архитектура разделяет **вычисления (Compute)** и **состояние/события (Storage & Event Streaming)**. Вычисления производятся на безлайтовых (Stateless) нодах, а PostgreSQL в связке с Sequin выступает единой платформой для данных и очередей сообщений.

```
                      +-------------------+
                      |   API Gateway /   |
                      |   Orchestrator    |
                      +---------+---------+
                                |
        +-----------------------+-----------------------+
        |                                               |
        v                                               v
+-------+---------------+                       +-------+---------------+
| Stateless Compute Node|                       | Stateless Compute Node|
|  (Go + Wasmtime)      |                       |  (Go + Wasmtime)      |
+-------+---------------+                       +-------+---------------+
    ^               |                               ^               |
    | (Push Event)  | (SQL: Checkpoint / Save)      | (Push Event)  | (SQL: Checkpoint / Save)
    |               v                               |               v
+---+---------------+-------------------------------+---------------+---+
|                                 Sequin                                |
+-----------------------------------+-----------------------------------+
                                    ^ (Logical Replication / WAL)
                                    |
                          +---------+---------+
                          |    PostgreSQL     |
                          | (Data & Tables)   |
                          +-------------------+
```

### Основные компоненты системы:
1. **Stateless Compute Nodes (Узел вычислений)**:
   * Хост-приложения на Go. Они не хранят состояние воркеров локально на диске.
   * Подписываются на поток задач от Sequin через долгоживущие HTTP-соединения (Server-Sent Events) или gRPC.
   * Получив задачу, выполняют её в `Wasmtime`, сохраняют измененное состояние в PostgreSQL по SQL и подтверждают (ACK) обработку задачи.

2. **PostgreSQL (Основное хранилище)**:
   * Хранит метаданные инстансов, Oplog и снапшоты памяти.
   * Изменения в таблицах пишутся в Write-Ahead Log (WAL), который является источником событий для Sequin.

3. **Sequin (CDC / Стриминг задач)**:
   * Подключается к PostgreSQL через механизм логической репликации и читает WAL.
   * Превращает изменения в таблицах (например, добавление новой задачи в `tasks` или изменение статуса воркера) в сообщения очереди.
   * Раздает задачи хост-нодам по модели Push (доставка событий), контролирует подтверждения (ACK) и таймауты видимости (Visibility Timeout).

## 2. Координация задач с помощью Sequin

Использование Sequin позволяет перейти от традиционной Pull-модели (опрос базы данных) к реактивной Push-модели.

### А. Устранение паразитного поллинга (DB Polling)
* **Проблема Pull-модели**: При использовании стандартного SQL-запроса `SKIP LOCKED` ноды вычислений вынуждены периодически опрашивать базу данных (например, раз в секунду). При отсутствии задач это генерирует тысячи холостых транзакций, перегружая CPU базы данных.
* **Решение Sequin (Push)**: Хост-нода устанавливает одно долгоживущее HTTP/gRPC соединение с Sequin. Если задач нет, поток «спит». Как только запись о задаче добавляется в PostgreSQL, Sequin мгновенно перехватывает WAL-событие и «пушит» (выталкивает) его в свободное соединение хост-ноды. Нагрузка холостого хода на PostgreSQL снижается практически до нуля.

### Б. At-Least-Once семантика и Failover
Sequin предоставляет полноценный API очереди сообщений поверх Postgres:
1. Хост-нода получает задачу из HTTP-стрима Sequin. С этого момента для задачи включается **Visibility Timeout** (например, 30 секунд). В течение этого времени задача не будет выдана другим нодам.
2. Хост-нода выполняет очередной шаг WASM-воркера и сохраняет чекпоинт в PostgreSQL.
3. После успешного сохранения хост-нода отправляет `ACK` (подтверждение) в Sequin. Задача удаляется из очереди или помечается как завершенная.
4. Если хост-нода падает (OOM, сбой сети) и не отправляет `ACK` в течение 30 секунд, Sequin автоматически возвращает задачу в очередь, и её получает другая хост-нода. Это гарантирует отказоустойчивость.

## 3. Оптимизация дискового ввода-вывода (I/O) в PostgreSQL

Для минимизации объема записываемых данных в PostgreSQL применяются следующие подходы:

1. **Редкие снапшоты памяти + частый Oplog**:
   * Большую часть времени хост записывает в таблицу `oplog` небольшие JSON/Binary-строки результатов внешних вызовов.
   * Снапшоты памяти (тяжелые BLOB-объекты) записываются не на каждом шаге, а только периодически (например, при завершении крупных логических этапов или каждые 50 шагов Oplog).

2. **Инкрементальное сохранение памяти (Dirty Pages)**:
   * Хост-нода отслеживает измененные страницы памяти WASM (размером по 4 KB) с момента последнего сохранения.
   * В таблицу `memory_deltas` записываются только изменившиеся страницы в формате `(instance_id, page_index, data)`.
   * При загрузке воркера хост считывает базовую память и накладывает измененные страницы. Это снижает дисковую нагрузку на PostgreSQL на **95%**.

## 4. Схема базы данных (Спецификация таблиц)

```sql
-- Таблица инстансов воркеров
CREATE TABLE instances (
    id UUID PRIMARY KEY,
    wasm_module_hash VARCHAR(64) NOT NULL,
    status VARCHAR(20) NOT NULL, -- 'pending', 'running', 'completed', 'failed'
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);

-- Таблица задач для Sequin (очередь)
CREATE TABLE tasks (
    id BIGSERIAL PRIMARY KEY,
    instance_id UUID REFERENCES instances(id) ON DELETE CASCADE,
    task_type VARCHAR(50) NOT NULL, -- 'run_step', 'resume'
    payload JSONB,
    created_at TIMESTAMP DEFAULT NOW()
);

-- Таблица журнала операций (Oplog)
CREATE TABLE oplog (
    instance_id UUID REFERENCES instances(id) ON DELETE CASCADE,
    call_index INT NOT NULL,     -- Порядковый номер внешнего вызова
    api_name VARCHAR(100) NOT NULL,
    request_payload BYTEA,
    response_payload BYTEA,
    created_at TIMESTAMP DEFAULT NOW(),
    PRIMARY KEY (instance_id, call_index)
);

-- Таблица инкрементальных страниц памяти (Delta Snapshots)
CREATE TABLE memory_deltas (
    instance_id UUID REFERENCES instances(id) ON DELETE CASCADE,
    page_index INT NOT NULL,     -- Номер страницы памяти (4KB блок)
    data BYTEA NOT NULL,         -- Содержимое страницы
    updated_at TIMESTAMP DEFAULT NOW(),
    PRIMARY KEY (instance_id, page_index)
);
```

### Настройка Sequin:
Sequin настраивается на прослушивание таблицы `tasks`. При вставке (`INSERT`) новой записи в `tasks` событие транслируется в соответствующий HTTP-consumer (наши Stateless Compute ноды).

## 5. Преимущества архитектуры на базе PostgreSQL и Sequin

* **Инфраструктурная простота**: Все данные, состояние и очереди лежат внутри одной базы данных PostgreSQL. Sequin работает рядом как сверхлегкий CDC-адаптер.
* **Push-модель доставки задач**: Исключает холостой поллинг БД нодами вычислений, сводя потребление ресурсов СУБД к минимуму.
* **Надежность доставки (At-Least-Once)**: Контроль видимости сообщений (Visibility Timeout) со стороны Sequin исключает потерю задач при сбоях исполнителей.
* **Масштабируемость**: Ноды вычислений могут горизонтально масштабироваться без создания паразитной конкуренции за блокировки таблиц. PostgreSQL легко справляется со стримингом WAL через логическую репликацию даже под высокими нагрузками.
