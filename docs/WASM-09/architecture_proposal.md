# Архитектурное предложение (Architecture Proposal): Распределенный Durable WASM на базе PostgreSQL

Цель данного предложения — спроектировать надежную и масштабируемую архитектуру для движка `durable-wasm`, используя в качестве единственного инфраструктурного бэкенда классическую СУБД **PostgreSQL**. Это позволяет избежать излишней сложности («технологической экзотики» вроде etcd, Redis или специализированных KV-хранилищ) на этапе масштабирования, сохраняя при этом гарантии отказоустойчивости (High Availability) и надежности выполнения бизнес-процессов (Exactly-Once).

---

## 1. Обзор целевой архитектуры

Архитектура разделяет **вычисления (Compute)** и **состояние/координацию (Storage & Orchestration)**. Все вычисления производятся на безлайтовых (Stateless) нодах, а PostgreSQL выступает единым источником правды для хранения данных и координации задач.

```
                      +-------------------+
                      |   API Gateway /   |
                      |   Orchestrator    |
                      +---------+---------+
                                |
        +-----------------------+-----------------------+
        |                                               |
        v                                               v
+-------+---------------+                       +-------+---------------+
| Stateless Compute Node|                       | Stateless Compute Node|
|  (Go + Wasmtime)      |                       |  (Go + Wasmtime)      |
+-------+---------------+                       +-------+---------------+
        |                                               |
        +-----------------------+-----------------------+
                                |
                                v
                      +-------------------+
                      |    PostgreSQL     |
                      | (Data & Locks &   |
                      |   Task Queue)     |
                      +-------------------+
```

### Основные компоненты системы:
1. **Stateless Compute Nodes (Узел вычислений)**:
   * Хост-приложения на Go, которые не хранят состояние воркеров на локальном диске (только кэшируют WASM-файлы).
   * Опрашивают PostgreSQL на предмет новых задач, запускают выполнение в `Wasmtime`, записывают чекпоинты и Oplog обратно в PostgreSQL.
   * Количество нод вычислений можно легко масштабировать в Kubernetes горизонтально.

2. **PostgreSQL (Единый бэкенд)**:
   * **Хранилище данных**: хранит метаданные инстансов, Oplog и снапшоты памяти.
   * **Очередь задач**: используется для распределения задач между нодами через стандартные транзакционные механизмы.
   * **Координатор блокировок**: предотвращает одновременный запуск одного воркера на разных нодах.

## 2. Координация задач и очереди средствами PostgreSQL

Использование PostgreSQL для очередей задач и блокировок убирает необходимость в etcd или Redis, обеспечивая строгую консистентность на уровне ACID транзакций.

### А. Распределенная очередь задач (Task Queue)
Для получения следующей задачи на выполнение хост-ноды выполняют атомарный запрос с конструкцией `SKIP LOCKED`:
```sql
UPDATE tasks
SET 
  status = 'running', 
  locked_by = :node_id, 
  locked_at = NOW(),
  updated_at = NOW()
WHERE id = (
    SELECT id FROM tasks 
    WHERE status = 'pending'
    ORDER BY priority DESC, created_at ASC
    LIMIT 1
    FOR UPDATE SKIP LOCKED
)
RETURNING instance_id;
```
* **Как это работает**: Конструкция `FOR UPDATE SKIP LOCKED` блокирует только одну выбираемую строку. Другие хост-ноды, выполняющие этот же запрос параллельно, просто «пропускают» заблокированную строку и мгновенно берут следующую свободную задачу. Это исключает задержки (contention) на запись.

### Б. Single-Active-Instance и Heartbeats
Чтобы гарантировать, что один воркер в один момент времени выполняется ровно на одном хосте:
1. При взятии задачи хост-нода накладывает блокировку на строку инстанса в таблице `instances` с помощью Advisory Lock:
   ```sql
   SELECT pg_try_advisory_xact_lock(:instance_id_hash);
   ```
   Либо использует колонку `locked_at` и `locked_by` с механизмом **Heartbeats**:
2. Во время выполнения долгоиграющего процесса хост-нода периодически (например, раз в 5 секунд) обновляет поле `locked_at = NOW()` для своего воркера в БД.
3. Если нода падает, ее блокировка устаревает (например, `locked_at < NOW() - INTERVAL '15 seconds'`). Другая нода может перехватить воркер, сбросив старую блокировку.

## 3. Оптимизация дискового ввода-вывода (I/O) в PostgreSQL

Для минимизации объема записываемых данных в PostgreSQL (решение проблемы Write Amplification) применяются следующие подходы:

1. **Редкие снапшоты памяти + частый Oplog**:
   * Большую часть времени хост записывает в таблицу `oplog` небольшие JSON/Binary-строки результатов внешних вызовов.
   * Снапшоты памяти (тяжелые BLOB-объекты) записываются не на каждом шаге, а только периодически (например, при завершении крупных логических этапов или каждые 50 шагов Oplog).

2. **Инкрементальное сохранение памяти (Dirty Pages)**:
   * Хост-нода отслеживает измененные страницы памяти WASM (размером по 4 KB) с момента последнего сохранения.
   * В таблицу `memory_deltas` записываются только изменившиеся страницы в формате `(instance_id, page_index, data)`.
   * При загрузке воркера хост считывает базовую память и накладывает измененные страницы. Это снижает дисковую нагрузку на PostgreSQL на **95%**.

## 4. Схема базы данных (Спецификация таблиц)

```sql
-- Таблица инстансов воркеров
CREATE TABLE instances (
    id UUID PRIMARY KEY,
    wasm_module_hash VARCHAR(64) NOT NULL,
    status VARCHAR(20) NOT NULL, -- 'pending', 'running', 'completed', 'failed'
    locked_by VARCHAR(100),      -- Идентификатор ноды-обработчика
    locked_at TIMESTAMP,         -- Время последнего heartbeat
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);

-- Индекс для быстрого поиска зависших задач и активных воркеров
CREATE INDEX idx_instances_status_lock ON instances(status, locked_at);

-- Таблица журнала операций (Oplog)
CREATE TABLE oplog (
    instance_id UUID REFERENCES instances(id) ON DELETE CASCADE,
    call_index INT NOT NULL,     -- Порядковый номер внешнего вызова
    api_name VARCHAR(100) NOT NULL,
    request_payload BYTEA,
    response_payload BYTEA,
    created_at TIMESTAMP DEFAULT NOW(),
    PRIMARY KEY (instance_id, call_index)
);

-- Таблица инкрементальных страниц памяти (Delta Snapshots)
CREATE TABLE memory_deltas (
    instance_id UUID REFERENCES instances(id) ON DELETE CASCADE,
    page_index INT NOT NULL,     -- Номер страницы памяти (4KB блок)
    data BYTEA NOT NULL,         -- Содержимое страницы
    updated_at TIMESTAMP DEFAULT NOW(),
    PRIMARY KEY (instance_id, page_index)
);
```

## 5. Преимущества архитектуры на базе PostgreSQL

* **Инфраструктурная простота**: Требуется только PostgreSQL. Никаких дополнительных распределенных очередей или хранилищ координирования.
* **ACID Гарантии**: Использование транзакций БД обеспечивает абсолютную надежность при распределении задач и исключает состояние гонки.
* **Масштабируемость**: Ноды вычислений полностью горизонтально масштабируемы. База данных PostgreSQL при оптимизированной записи (инкрементальные снапшоты + Oplog) способна обрабатывать тысячи транзакций в секунду на стандартном оборудовании. При необходимости дальнейшего роста СУБД может быть переведена на кластерную репликацию или CockroachDB без изменения логики Go-приложения (так как CockroachDB совместима с протоколом PostgreSQL).
