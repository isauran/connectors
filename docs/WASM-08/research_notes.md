# Исследование архитектуры Golem Cloud и сопоставление с движком durable-wasm

Этот документ содержит детальный анализ архитектурных концепций платформы Golem Cloud (лидера в области Durable WebAssembly), их сопоставление с текущей реализацией `durable-wasm` и анализ ограничений использования SQLite в качестве хранилища состояний воркеров.

---

## 1. Архитектурные основы Golem Cloud

Платформа **Golem Cloud** разработана для обеспечения отказоустойчивого выполнения произвольного кода (Durable Execution) без изменения исходного кода приложения. Она базируется на технологии WebAssembly и использует подход **Event Sourcing** и **виртуализацию системных вызовов**.

### А. Детерминизм выполнения (Deterministic Execution)
Golem Cloud компилирует исходный код (Rust, Go, Python и др.) в стандартный бинарный формат WASM. Поскольку среда выполнения WebAssembly является изолированной песчаницей, рантайм полностью контролирует внешние воздействия. При одинаковом начальном состоянии памяти и детерминированном поведении процессора, повторное выполнение того же набора инструкций гарантированно приведет к тому же самому результату.

### Б. Автоматический Oplog (Operation Log) и перехват WASI
В отличие от Temporal или Camunda, где разработчик обязан оборачивать любые внешние вызовы (сайд-эффекты) в специальные конструкции (Activity/External Task), Golem Cloud решает эту проблему прозрачно на уровне виртуальной машины:
1. **Перехват импортов (WASI Virtualization)**: Golem подменяет стандартные системные вызовы WASI (работа с сетью, чтение системного времени, генерация случайных чисел).
2. **Запись в Oplog**: При первом выполнении воркером сетевого вызова (например, отправка HTTP-запроса через стандартную библиотеку языка), рантайм Golem осуществляет реальный запрос, получает ответ и сериализует его в журнал операций (Oplog).
3. **Фаза Replay (Повторное воспроизведение)**: Если воркер прерывает работу (из-за аварии сервера или миграции на другой узел), он восстанавливается с последнего чекпоинта и начинает выполняться заново. Когда код доходит до того же вызова WASI, хост-система не отправляет сетевой запрос повторно, а мгновенно возвращает результат из Oplog.
4. **Exactly-Once Semantics**: Это гарантирует, что внешние системы увидят ровно один вызов, а логика приложения выполнится последовательно.

### В. Инкрементальные снимки памяти (Dirty-Page Snapshots)
Для минимизации времени восстановления (Replay) долгоживущих процессов Golem периодически сохраняет снимки оперативной памяти (Linear Memory) воркера.
* **Проблема полного снимка**: Сохранение всей линейной памяти WASM-модуля (которая может составлять от нескольких мегабайт до гигабайт) при каждом чекпоинте неэффективно и создает колоссальную нагрузку на дисковую подсистему.
* **Решение Golem**: Рантайм на базе Wasmtime отслеживает измененные страницы памяти (Dirty Pages) размером 4 KB с момента последнего сохранения. На диск записываются только дельты (измененные страницы и их смещения). При восстановлении рантайм накладывает эти дельты на базовый снимок памяти WASM-модуля.

## 2. Анализ ограничений SQLite в Durable WASM

В текущей версии `durable-wasm` в качестве хранилища состояния используется SQLite, реплицируемый в S3 с помощью Litestream. Это решение отлично подходит для простых сценариев, но имеет критические ограничения при масштабировании.

### 1. Write Amplification (Избыточная запись на диск)
В `durable-wasm` сохранение состояния воркера реализовано как запись полного бинарного образа памяти (Whole-Memory Snapshot) в BLOB-поле SQLite:
* Если WASM-воркер использует 4 МБ памяти и делает 10 последовательных шагов (например, HTTP-запросы с чекпоинтом после каждого шага), рантайм запишет в SQLite в общей сложности **40 МБ данных**.
* Это приводит к быстрому износу SSD-накопителей и генерирует огромный объем транзакционных логов (WAL).
* Репликатор Litestream вынужден отправлять терабайты WAL-файлов в S3, что перегружает сеть.

### 2. Сериализация операций записи (Locking)
SQLite спроектирована как локальная встраиваемая база данных:
* Несмотря на поддержку параллельного чтения в режиме WAL, запись в базу данных всегда **сериализуется**. В один момент времени писать в файл базы данных может только один поток.
* При высокой конкурентности (сотни параллельно работающих воркеров, одновременно вызывающих `checkpoint()`) транзакции записи выстраиваются в очередь. Это приводит к ошибкам типа `database is locked` или сильному падению производительности (latency).

### 3. Фрагментация и раздувание файла базы данных (Database Bloat)
При частом обновлении и перезаписи больших BLOB-объектов в SQLite:
* Удаленные или обновленные страницы данных не возвращаются операционной системе автоматически, а помечаются как свободные внутри структуры SQLite (`freelist`).
* Файл базы данных на диске продолжает расти. Для его сжатия требуется выполнение команды `VACUUM`, которая полностью блокирует базу данных для чтения и записи на время выполнения, что неприемлемо для систем реального времени.

## 3. Сравнительный анализ: Golem Cloud vs Durable WASM

| Критерий сравнения | Golem Cloud | Наш `durable-wasm` |
| :--- | :--- | :--- |
| **Сложность воркера** | **Низкая**. Разработчик пишет обычный синхронный/асинхронный код без стейт-машин. | **Средняя**. Требуется вручную описывать шаги (`switch step`) и вызывать `checkpoint()`. |
| **Управление сайд-эффектами** | **Автоматическое**. Сетевые вызовы перехватываются на уровне WASI и логируются в Oplog. | **Ручное**. Разработчик должен сам сохранять результаты вызовов в состояние перед чекпоинтом. |
| **Снимки памяти (Snapshots)** | **Инкрементальные (Delta)**. Записываются только измененные 4KB страницы памяти. | **Полные (Whole-Memory)**. Каждый чекпоинт записывает всю линейную память WASM-модуля. |
| **СУБД / Хранилище** | Распределенное Key-Value хранилище (собственная реализация на Rust/Raft). | SQLite (локальный файл) + Litestream репликация в S3. |
| **Масштабируемость** | Выдерживает миллионы параллельных воркеров благодаря распределенной архитектуре. | Ограничена пропускной способностью диска и последовательной записью SQLite. |

## 4. Рекомендации по развитию `durable-wasm`

Для преодоления ограничений SQLite и приближения функционала к уровню Golem Cloud рекомендуется реализовать следующие оптимизации:

### Рекомендация 1. Переход на инкрементальные снапшоты (Dirty-Page Tracking)
Вместо сохранения всей памяти WASM-модуля при каждом чекпоинте:
1. Использовать API Wasmtime для получения списка модифицированных страниц памяти (или сравнивать блоки памяти хост-кодом).
2. Записывать в SQLite таблицу `memory_deltas` записи вида `(instance_id, block_index, data_blob)`.
3. При восстановлении воркера загружать базовый WASM-модуль и последовательно накатывать измененные блоки из БД.
4. Это снизит Write Amplification в **10–100 раз** и кардинально уменьшит трафик Litestream.

### Рекомендация 2. Легковесный Oplog на уровне хоста
Для устранения ручного написания шагов (`switch step`) в коде воркеров:
1. Создать в SQLite таблицу `oplog` со структурой: `(instance_id, call_index, api_name, request_payload, response_payload)`.
2. Реализовать на стороне Go-хоста функции-импорты для выполнения HTTP-запросов.
3. При вызове функции из WASM, хост проверяет, есть ли запись для `call_index` в таблице `oplog`. Если есть — возвращает сохраненный `response_payload`. Если нет — делает реальный вызов, сохраняет результат в БД и возвращает его в WASM.
4. Это позволит писать воркеры как линейный детерминированный код.
