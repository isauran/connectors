# Durable WASM Stability Analysis & Testing Strategy

Этот документ содержит детальный анализ стабильности пакета `durable-wasm`, выявляет потенциальные точки отказа и утечки ресурсов, а также предлагает стратегию повышения надежности с помощью новых тест-кейсов.

---

## Текущее состояние стабильности

Архитектура `durable-wasm` уже содержит ключевые защитные механизмы:
* **NaN Canonicalization**: В Wasmtime включена строгая детерминированность чисел с плавающей точкой, что предотвращает расхождение состояний при восстановлении (replay).
* **OCC (Optimistic Concurrency Control) Fencing**: Версионирование метаданных в БД блокирует одновременное выполнение одного инстанса на разных хостах (защита от split-brain).
* **Oplog & Delta Truncation**: Периодическое сжатие лога и создание полных снапшотов предотвращают бесконечный рост базы данных.

Тем не менее, при работе в высоконагруженном продакшн-окружении с частыми сетевыми сбоями и высокой конкурентностью могут возникнуть проблемы с утечкой ресурсов.

---

## Потенциальные точки отказа и утечки ресурсов

### 1. Утечка файловых дескрипторов (TCP-соединений)
Каждый раз, когда вызывается `NewEngine`, создается новый объект `http.Client`:
```go
httpClient: &http.Client{
    Timeout: 30 * time.Second,
    Transport: &http.Transport{
        MaxIdleConns:        100,
        MaxIdleConnsPerHost: 10,
        IdleConnTimeout:     90 * time.Second,
    },
}
```
If your application creates `Engine` instances dynamically per request or goroutine, it will create hundreds of TCP connection pools. The connections will hang in the `TIME_WAIT` state for up to 90 seconds (`IdleConnTimeout`), which can cause free socket exhaustion on the server (Socket Exhaustion).

**Решение**:
* Позволить передавать переиспользуемый `http.Client` (или `http.RoundTripper`) в `NewEngine` (например, через функциональные опции `Option`).
* По умолчанию использовать global оптимизированный HTTP-клиент.

### 2. Зависание горутин выгрузки (`handleUpload`)
В функции `handleUpload` запускается асинхронная горутина для стриминга данных по сети:
```go
go func() {
    resp, err := httpstream.NewRequest(context.Background(), *s.engine.httpClient, "POST", url).
        Body(pipeReader, "application/octet-stream").
        Send()
    ...
}()
```
Она использует `context.Background()`. Если выполнение WASM аварийно завершится (например, из-за паники или ошибки в Wasm-коде), функция `Execute` выйдет, закрыв `session.uploadPipeW`. 
Хотя закрытие пайпа разблокирует чтение в `pipeReader`, сам HTTP-запрос (если он завис на этапе установления TLS-соединения с внешним сервером) будет ждать 30 секунд (таймаут HTTP-клиента). До этого момента горутина будет висеть в памяти.

**Решение**:
* Связать жизненный цикл горутины выгрузки с контекстом выполнения сессии `Session`.
* Создавать `context.WithCancel` при старте `Execute` и отменять его при выходе, чтобы мгновенно прерывать любые зависшие сетевые запросы.

### 3. Очистка C-ресурсов Wasmtime
Wasmtime написан на Rust, и его Go-биндинги используют `cgo`. Объекты `Store`, `Engine`, `Module` выделяют память вне кучи Go (в C-куче). Go GC освобождает их через `runtime.SetFinalizer`, но в сценариях с частым созданием короткоживущих инстансов `Store` память в C-куче может расти быстрее, чем GC успевает запускать финализаторы.

**Решение**:
* Wasmtime в Go предоставляет метод `Store.Close()` (или `linker.Close()`). Хотя в текущей версии `Execute` создается локальный `store := wasmtime.NewStore(e.wasmEngine)`, явный вызов освобождения ресурсов при выходе из `Execute` повысит стабильность по памяти.

## Стратегия тестирования для повышения стабильности

Для достижения максимальной стабильности рекомендуется покрыть кодовую базу следующими классами тестов:

### 1. Тесты инъекции ошибок БД (Storage Error Injection)
Проверка того, как ведет себя движок при внезапных ошибках SnapshotStore (например, переполнение диска, разрыв соединения с PostgreSQL).
* **Сценарий**: Подсунуть мок-реализацию `SnapshotStore`, которая возвращает ошибки `io.ErrUnexpectedEOF` или `sql.ErrConnDone` на методах `Save`, `SaveDeltas`, `SaveOplog`.
* **Ожидание**: Движок должен корректно аварийно завершать выполнение, возвращать ошибку вызывающему коду, закрывать все HTTP-соединения и сетевые пайпы, не зависать и не падать в panic.

### 2. Тесты отмены контекста (Cancellation Tests)
Проверка корректной отмены долгоиграющих задач.
* **Сценарий**: Запустить WASM-инстанс, выполняющий тяжелый стриминг данных (`handleDownload` или `handleUpload`), и через 100 миллисекунд отменить контекст, переданный в `Execute` (понадобится добавить `context.Context` в сигнатуру `Execute`).
* **Ожидание**: Все сетевые операции должны немедленно прекратиться, горутины — завершиться, ресурсы — высвободиться.

### 3. Стресс-тест на утечку памяти и дескрипторов (Leak & Soak Testing)
* **Сценарий**: Циклический запуск 1000 коротких WASM-инстансов с чекпоинтами и сетевыми вызовами. 
* **Ожидание**: Мониторинг количества открытых файлов (`lsof`), сетевых соединений в состоянии `TIME_WAIT` и потребления памяти (через `runtime.ReadMemStats`). Значения должны стабилизироваться и не расти линейно.

### 4. Тесты устойчивости к невалидным Wasm-модулям (Fuzzing / Panic Protection)
* **Сценарий**: Передача в `Execute` поврежденных WASM-файлов или модулей, которые делят на ноль, выходят за пределы памяти (out-of-bounds memory access) или вызывают бесконечный цикл.
* **Ожидание**: Wasmtime должен перехватывать эти ловушки (traps) и возвращать ошибку, не роняя весь Go-процесс.
